# Private offline navigation boundary design — no production capability

**Status: RESEARCH ONLY; no live method, route, MCP tool, deployment, or movement permit.** `src/navigation-service-boundary.ts` anchors the service's disabled `pinGo` claims and an unsatisfiable admission preflight. `src/navigation-controller.ts` is a fake-transport research controller; its test-only idle seed is not a production grant. The service supplies null active-map/pose/transform/readiness/supervision/route evidence. A cached V1 raster, status-derived map ID candidate, map header index, dock marker, receipt time, trace and page click cannot establish current localization. No pose-specific timestamp, verified active-map binding, display-to-robot transform or physical stop proof exists.

## Proposed future separation, requiring distinct owner-reviewed changes

1. Service is sole authority for admission and audit, per selected robot/session and exclusive navigation lease. It must obtain independently time-stamped current pose, independently verified active map bound to the same selected device/map, calibrated common map frame including orientation/origin/rotation, fresh idle/task/lock/error/arm/chassis readiness, owner presence with accessible physical stop, and route/footprint/obstacle clearance. Enforce `assessPinGo` on NEW evidence immediately before each one-shot action, match the proposed target exactly to the checked transform, reject extra/unknown payload keys, unsafe numeric values, bounds and frame mismatches. Frontend normalized pixel drafts must never be promoted to robot coordinates by client assertion. Current fake gate is necessary but not sufficient: it trusts externally supplied `verification` strings and has no observation provenance. Service must own the evidence acquisition and provenance, not accept it from HTTP/MCP. No command from stale/missing pose, map, route or stop proof.
2. A separately audited navigation-specific wire policy (not the generic `SupervisedCommand` union or `RobotClient.request` read allowlist) would be the sole place to admit **one** verified `app_goto_target` with precisely documented Z70 coordinate payload, frame and numeric limits. The Android plugin wrapper is only a static candidate: wire shape, ACK and firmware support remain unverified. The dedicated adapter must require already-connected same LAN session, no reconnect/backlog/replay, one reserved dispatch per lease, and freeze validated coordinates before yielding; isolate it from browser RC and agent pulse claims. Until reviewed, do **not** add either movement RPC to `robot.ts` METHODS or expose a route/tool.
3. A **separate navigation-specific prioritized `stop_goto_target` path** (alternate plugin protocol names `user.stop_goto_target`; neither is yet validated on this robot) must bypass waiting on target ACK, service read, regular motion queue, map-refresh exclusivity and dispatch lock; privilege to stop should not require fresh pose or map, but must bind the selected robot/session and reject malformed input. It must not be substituted with `app_stop` cleaning cancel, `app_rc_stop` or `/api/agent/stop`. The current generic agent STOP stops RC only; its successful HTTP response cannot represent navigation cessation. Prioritize without promising that local send order equals device execution order. Lost stop ACK, disconnect, reordered/late target ACK, stop timeout and restart mean *may still move*; do not clear the latch. After target could have been sent, a stop ACK plus a later idle sample is insufficient without verified ordering and sustained independent physical observation. Tell nearby owner to use physical emergency stop on uncertain motion or hazards.
4. Monitor continuously during an authorized navigation lease: independently fresh pose/active-map identity, task mode, route and obstacle clearance, connection and human supervision; watchdog on stale/missing samples, map switches, task conflicts, lease expiry, unexpected movement and client loss. Trigger independent stop and physical abort on failures, retain a conservative UNKNOWN latch across process restart. Arrival ACK, state bits or a single image do not prove stationary. A separately validated ordered-abort/cessation protocol and nearby owner physical observation are required to release uncertainty; until then no second target. No automatic replay on timeouts, late responses or reconnection. Audit only bounded event kinds/times/reasons, not home coordinates or private map bytes.
5. Only after hardware stop trials with a nearby owner, protocol validation, proof of pose/map/frame and monitor, threat review and explicit deployment authorization could a narrow service route be considered, with browser authorization and CSRF and a separately permission-scoped MCP action decision. Tests of source alone are not robot safety evidence.

## Existing boundary references

- `src/control-policy.ts`: fixed supervised RPC command union; must not receive a raw target case through ordinary chassis motion.
- `src/robot.ts`: read-method allowlist plus prioritized RC stop queue; it cannot prove priority delivery or navigation stop semantics.
- `src/service.ts`: route allowlist, agent STOP, map refresh exclusivity and always-disabled `pinGo` state; no navigation action route.
- `src/navigation-controller.ts` / `src/pin-go-gate.ts`: synthetic attempt/lease, no replay, unknown latch and independent priority-stop shape; not service-attached and not an actual active-map/pose source.
