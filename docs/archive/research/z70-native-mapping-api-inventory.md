# Z70 stock API inventory for independent native DimOS mapping

Static research: 2026-10-06. **No robot reads, camera activation/capture, motion, mapping run, mode changes, deployment, or commits.** Only this document was written. The saved-map private files were not opened; their research summary was sufficient. No private URLs, credentials, identifiers or home geometry are reproduced.

## Verdict

The inspected stock interface positively supports vendor map/diff observations, a switched RGB viewing path, status/arm queries, and vendor point-navigation commands. It does **not yet establish a qualified independent metric mapping input** for native DimOS. This is an interface-evidence limitation, not proof that firmware lacks internal sensors or that every possible stock API has been exhausted.

The highest-value stock-only route is to qualify the existing RGB stream and inspect the native video bridge for original frame timing/metadata, while finishing the offline dynamic-map decoder. The latter is useful as a **separate vendor observer/comparison channel**, not an independent mapper. No raw LiDAR, depth, stereo pair, IMU or encoder stream was positively traced in this plugin. Extra hardware is a conditional fallback only after stock data qualification, not the assumed starting point.

The experiment remains: construct a native DimOS map from independent observations, save it, then compare against the saved Roborock map offline. Vendor raster, vendor paths and vendor map-localized pose must not supply geometry, localization prior, scale fitting or ground truth to construction. Even RGB geometry accumulated using vendor-map pose would be a vendor-assisted reconstruction, not the strict independent experiment.

### Timing and map dependence

H #12147 throttles diff requests using app elapsed time: thresholds 1.2 seconds outside Mi app, 1.4 seconds in Mi app, and 2 seconds in a delayed-diff condition. Requests can also be suppressed while locating or awaiting handling. These are scheduling lower bounds under conditions, **not delivered frequencies** (nominal ceilings roughly 0.83/0.71/0.5 requests per second). Push reports can take another path; their frequency is unknown. Neither changing x/y nor increasing `msg_id` demonstrates when firmware captured the pose.

The date schema above warrants offline examination, but a separately encoded map date must not be promoted into a pose clock without a semantic and association proof. Saved-map receipt/cache time likewise is not capture time or fresh localization. See `roborock-map-reference.md`; no private geometry needs copying here.

## Sensor opportunity inventory: what is not established

A full function-block lexical scan of this disassembly found zero owning functions for `pointcloud`, `point_cloud`, `intrinsics`, `quaternion`, `odometry`, `imu_data`, `depth_data`, `get_pose`, `get_position`; `lidar` occurred in eight blocks, including false substring matches such as `checkValidArgs`. The meaningful #5104 path reads `RRPluginSDK.supportLidar`; #5738 calls `is3DMapSupported`, `isSupport3DMap`, `isSupportLidar`. These are capability/feature checks, **not scan subscriptions or range arrays**. Their name is not evidence that Z70 has an exposed conventional LDS stream. `arm_view` was found in #28235, whose body renders pickup controls/text and an image asset—not arm-camera depth data.

No concrete export was established for:

- raw laser beams (angles/ranges/intensity/scan clock), posed 3D points, ToF/depth matrices, stereo simultaneous frames/baseline;
- camera fx/fy/cx/cy, distortion, exposure clock, hardware synchronization or fixed camera-to-base extrinsics;
- wheel ticks/encoder odometry, acceleration/angular-rate IMU, quaternion orientation, fused metric velocity/covariance.

These remain **unknown/unexposed in the inspected path**, not impossible firmware capabilities. Generic graphics `depth`/matrix libraries, smartphone sensors and UI position fields are not robot sensor streams. Connected phone IMU could only describe the phone unless rigid mounting, clock and extrinsics were deliberately qualified.

### Cloud/local encryption is a separate issue

`photo-protocol.ts` positively distinguishes protocol-301 photo blobs (ROBOROCK envelope, request ID, gzip) from nonce-keyed AES-CBC/gzip map replies. `cloud-map-list-v1-research.ts` checks V1 outer frame/CRC, decrypts selected-key payload and correlates DPS-102 JSON request ID. This does not decode every native split-map or dynamic payload or prove method/map/freshness semantics. Successful saved V1 decoding must not be generalized to raw sensor streams. Resolve nested payload validation/schema, native versus V1 coordinate namespace, split correlation, date semantics and device binding independently. No generic “encrypted therefore inaccessible” conclusion is warranted; no evidence that decryption yields raw LiDAR was found either.

## Native DimOS reuse and realistic paths

Native port requirements and source revisions are documented in `dimos-native-sock-pickup.md`; do not invent another SLAM stack.

1. **Stock RGB qualification first.** Reuse existing go2rtc/video acquisition and native `Image`/memory recorder; inspect RRVideo native capture/record callbacks and original video PTS/clock metadata offline. Establish lens identity, calibration at exact resolution, distortion, rigid mounting and camera-to-base TF. A chassis camera is preferable for stable extrinsics. A moving arm camera requires synchronized measured joint/mount pose; uncalibrated arm array cannot supply it. Switched front/arm cameras are not stereo, and switching breaks single-camera calibration/trajectory continuity.
2. **Independent camera mapping only if input requirements are met.** Native `DimSlam` has calibrated image/depth/CameraInfo and optional configured IMU/odometry inputs. Current JPEG alone is not the documented qualified RGB-D/stereo mapping pipeline. Monocular structure-from-motion has scale ambiguity; known robot size, arm step model, JPEG dimensions or commanded speed do not automatically resolve it. Independently surveyed markers/known camera height and constrained floor observations may provide metric constraints in a supported existing pipeline, but restricted floor-plane projection is not general depth or volumetric mapping. Check native backend's supported mono/scale configuration before promising a stock-only map; no custom SLAM or generated depth masquerading as measured depth.
3. **If genuine stock depth/scan export is later found, qualify it before adding hardware.** Supply actual timestamped `Image` depth + matching `CameraInfo` to native `DimSlam`, or metric `PointCloud2` plus independently estimated pose/TF to native mapping. `VoxelGridMapper` requires world-frame clouds and is not a localization estimator. A 2D scan with invented z=0 does not magically provide native 3D relocalization observability; assess an existing supported pipeline rather than disguising a planar scan as rich 3D.
4. **Keep vendor observer separate.** Complete bounded offline dynamic decoder/date investigation and later separately authorized data capture for map/pose comparison. Vendor x/y/angle can help describe firmware behavior and eventual native-goal frame registration, but remain vendor-map-derived until proven otherwise. Do not feed them into strict independent construction. RC `{velocity,omega,duration,seqnum}` is a vendor command interface; integrating requests is not measured odometry.
5. **Conditional extra hardware.** If stock qualified inputs cannot be obtained, choose an existing supported calibrated RGB-D/stereo sensor with native `DimSlam`, or coherent LiDAR+IMU/PointLIO integration, only after explicit hardware choice. Rigid mount, power/network/compute capacity, payload/clearance, occlusion, camera range and vacuum low viewpoint need checking. A separate hand-carried survey can independently map the floor but is not a stock Z70 sensor demonstration or onboard localization. Reuse native memory → mapping/export → native costmap/planner; only a small transport/type/frame bridge should be custom.

## Data qualification deliverable before a physical mapping experiment

Use already retained authorized recordings/nonprivate fixtures first. Any new sensor session or survey is separately authorized, not executed by this static task.

- Per stream: actual method/subscription/SDK callback, selected device/lens, payload schema, raw versus firmware-derived provenance, units/axes, calibration source and transform chain.
- Timing: exposure/scan timestamp versus PTS versus app receipt; clock mapping/uncertainty, monotonically increasing sensor sequence, observed rate distribution, latency/jitter/drop/replay and sensor synchronization. Report measurements rather than SDK maximums.
- Metric independence: scale from independent calibration; no vendor map prior/pose in construction. If a vendor pose is used for an alternative, label it vendor-assisted and retain separate results.
- Offline replay through native `DimSlam` or appropriate existing native sensor pipeline; inspect tracking loss, drift, loop consistency, wall/door geometry, coverage and uncertainty. Save typed recordings and native map artifact, not an extruded vendor raster.
- Only after construction, register independently observed common landmarks to compare floor projections against the saved reference; report transform uncertainty, overlap and missing/dynamic geometry. Neither result is automatically ground truth.

**Next static work with best expected value:** finish #12658 helper/signedness and #12683 date semantics using offline fixtures; inspect parent APK DEX/native RRVideo capture and metadata contracts; test already available RGB recordings for calibration/timing suitability. These are concrete opportunities, not permission to activate the robot. No service policy gates, readiness locks or admission restrictions are proposed or restored.
