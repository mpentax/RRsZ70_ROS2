# Pure command ownership core

`src/command-arbiter.ts` is an offline admission/state machine, not a ROS bridge, transport, permission grant, or safety-rated interlock. It has no robot imports, wire methods, timers, automatic retry, or live traffic. All browser/MCP/future ROS writers must eventually share **one authoritative instance per service**, not separate arbiters. Calls are synchronous; within that instance reservation and dispatch transitions are atomic against interleaved callers. It provides no cross-process/distributed locking or hard realtime guarantee.

## Exact integration API

- `new CommandArbiter(deviceId, {now, maxLeaseMs?, maxCommandMs?})`: injected monotonically nondecreasing integer-millisecond clock; defaults 30s lease/10s dispatch deadline, maximum configuration 60s. Clock regression fails closed.
- `acquire({writer: 'browser'|'mcp'|'ros', sessionId}, ttlMs)`: exclusive device/session-bound lease; returns `{id, writer, sessionId, deviceId, expiresAt}`. Competing acquisition is rejected, including same owner. Do not trust caller-supplied session identity: authenticate upstream.
- `renew(leaseId, owner, ttlMs)`: only matching current owner; expiry cannot resurrect ownership. `revoke(leaseId)` is a privileged service lifecycle operation, not a client authorization boundary.
- `reserveAction(commandId, leaseId, owner, timeoutMs)`: consumes unique ID and reserves one action. Pending action or any unresolved latch blocks admission. `beginDispatch(commandId, owner)` transitions reserved action once; rechecks lease, deadline, device, and uncertainty. Call **immediately before** dispatch, without an async gap to other admission operations.
- `requestStop(commandId, timeoutMs)` and `beginDispatch(commandId)` admit stop independently of leases, pending action, and unknown latches. Upstream authorization/rate limits still apply. Use a separately available priority stop adapter; do not queue behind a blocked action promise. This is a stop request, not verified cessation.
- `acknowledge(commandId, deviceId)` records correlated transport acknowledgement, never physical completion. Late ACK leaves unknown latched. An acknowledged action remains pending: no second action is admitted until `finishAction` supplies trusted terminal evidence. Independent stop admission remains available. Upstream must validate real request/device correlation rather than accepting client assertions.
- `finishAction({commandId, deviceId, kind, evidenceId})`: trusted correlated terminal evidence moves an action from dispatching/acknowledged/unknown to `completed`, clearing its latch if present. Uses the same two explicit evidence kinds as clearance below. Upstream must authenticate evidence provenance and verify cessation **and absence of pending/delayed execution**, or prove no dispatch occurred. ACK and idle alone are forbidden evidence. Completed IDs remain consumed across restart.
- `markUnknown(commandId, reason)` marks dispatched/acknowledged work ambiguous, e.g. timeout, connection loss, or unverified execution outcome. No automatic replay.
- `clearUnknown({commandId, deviceId, kind, evidenceId})`: explicit trusted evidence assertion. Kind is `verified-cessation-and-no-pending-execution` or `verified-not-dispatched`. The core cannot acquire/validate physical evidence: the service must enforce provenance, freshness, correlation, and absence of delayed remote execution. Idle telemetry, ACK, elapsed time, stop ACK, and a device switch are **not** clearance. History remains unknown and ID consumed after clearance.
- `tick()`: expire lease, cancel unissued reservations, latch issued commands when their ACK deadline expires. Invoke on service scheduler ticks and lifecycle events; all public boundary operations also tick. Timer stalls can delay detection; lease expiry does not halt a motor.
- `changeDevice(deviceId)`: invalidates ownership/reservations; pending issued or acknowledged-but-unverified actions latch against the old device. Old-device uncertainty conservatively blocks all new action acquisition until explicitly resolved. Stop requests target the currently selected device; this does not stop the previous device.
- `snapshot()`: defensive serializable v1 snapshot including consumed IDs and unknown latches. `CommandArbiter.restore(snapshot, options)`: drops leases, cancels reserved work, converts in-flight dispatch and acknowledged-but-unverified action execution to unknown, retains consumed IDs/latches. No work is resumed.

## Persistence and adapter sequencing

Before invoking transport, durably store the snapshot **after** `beginDispatch`. If persistence fails, do not dispatch; mark uncertain or supply verified-not-dispatched evidence as appropriate. Persist all mutations, especially latches and clearance, and do not accept new work until initial restore succeeds. The pure core does not do storage or asynchronous transactions. Crash after persistence but before actual send is conservatively unknown. Crash after send but before ACK persistence is also unknown. Never restore an old checkpoint, silently reset history, prune IDs, or create a fresh controller to bypass uncertainty. The history intentionally grows: integrations need a durable lifetime ID ledger before introducing compaction.

Existing transport execution remains separately controlled. Service adapters must fence other writers, avoid async gaps between the final guard and issuance, serialize durable updates, and explicitly surface disconnect/restart ambiguity. Acknowledgement is only a transport state; adapters must call `markUnknown` when physical execution remains unresolved under their action semantics. This core does not infer that acknowledged actions have finished: they stay pending even past the ACK deadline until terminal evidence arrives or ownership loss/restart latches uncertainty. Lease expiry/revocation also latches acknowledged actions. `clearUnknown` alone is not action completion: an action must use `finishAction` to establish its completed terminal state; neither API accepts bare ACK or idle evidence. Existing busy/motion/arm readiness guards remain required. A future ROS action bridge should map admissions and correlated outcomes to goal states without claiming motor cessation or treating action cancellation as physical stop.
