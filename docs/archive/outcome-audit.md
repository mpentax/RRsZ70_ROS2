# Legacy outcome audit (offline, 2026-09-30)

## Evidence rules

HTTP receipt, service acceptance, robot RPC ACK, robot-reported mode/readiness and physical completion are different evidence. Timeout, connection loss, invalid response and uncorrelated state cannot prove nonexecution. Busy rejection of a new request does not resolve a prior request. No ambiguous action is automatically retried. Physical verification remains external to these helpers.

## Implemented in owned files

- `src/action-outcome.ts`: typed unknown/rejected/accepted/in-progress/acknowledged evidence; response origin, timeout versus HTTP/transport error; nullable ACK; unverified physical completion; no automatic retry. Explicit request-ID-correlated robot rejection can classify rejection. Same-request late ACK can reconcile unknown to acknowledged only, not physical success. This is a pure helper, not a live late-response collector.
- `src/mcp-server.ts` action errors formerly emitted `acknowledged:false` even when no response arrived, and 409 explanation asserted rejection despite possible controller-origin post-dispatch errors. Now errors preserve `acknowledged:null`, unknown execution, local-service versus MCP transport origin, safe conflict explanation and no automatic retry. No upstream body/error message is echoed.
- MCP state-only, `stopped:true`, HTTP 200, or missing ACK do not become ACK. Busy/preparing state is in-progress; explicit accepted reply is accepted. Robot ACK is explicitly reported as service-reported robot evidence, never physical completion. Safe field filtering retained.
- All MCP action descriptions now state HTTP success is not physical success, missing ACK/timeouts/busy do not settle execution, and automatic retry is forbidden. Pulse cessation and manual workflow readiness caveats added in `mcp-actions.ts`.
- Tests: `action-outcome.test.ts`, additions to `mcp-actions.test.ts`, existing `mcp-server.test.ts`: classifications, false/missing ACK, 409/502, preparing, stop flag, accepted, correlated versus mismatched late ACK, rejection, no retries, redaction and all LLM-facing descriptions.

## P2 follow-up: typed MCP propagation (2026-09-30)

- Added a shared closed-enum validator for the complete existing `ActionOutcome` shape. Valid nested `actionOutcome` or direct envelopes outrank legacy busy/phase inference; additive fields are stripped. Invalid envelopes fall back to legacy evidence/unknown, not physical success. Rejection cannot contain ACK=true; acknowledgement requires ACK=true. All envelopes require unverified physical completion and no automatic retries.
- MCP success replies preserve the validated envelope and classify before legacy filtering. Arbitrary top-level error text is no longer returned. Legacy `acknowledged:false` plus busy remains in-progress, not rejection.
- Action non-2xx replies now parse only JSON with a 16 KiB actual-byte and declared-length limit. Only validated outcome evidence and closed `NEEDS_VERIFICATION` staging metadata survive. Malformed, oversized, wrong-content-type, read-error and arbitrary upstream messages remain generic unknown HTTP evidence. Legacy HTTP 409 alone remains ambiguous. No replay or additional request is introduced.
- Dock listing now explicitly advertises unavailable/staging-only status, trusted physical-stow verification and shared reservation prerequisites. A service rejection with `stage:NEEDS_VERIFICATION` retains that machine-readable stage, `availability:staging-only`, and false navigation/physical-verification flags. Docking remains intentionally incomplete and fail-closed; this change does not wire or authorize native docking.
- Compatible with service-generated `{actionOutcome: ActionOutcome}` and the direct envelope form. `reason` retains its existing closed enum; docking's workflow reason is separately retained as `stage`, rather than widening the enum to arbitrary upstream strings.
- Offline targeted verification: `node --test src/action-outcome.test.ts src/mcp-actions.test.ts src/mcp-server.test.ts`: **15 passed, 0 failed**. `npm run typecheck`: passed (server and web). No live robot/service calls, permission changes, restarts, commits or pushes.
