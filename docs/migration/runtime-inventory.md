# Runtime ownership, imports and entrypoints — phase 1 inventory

## Scope and reading rules

This is an **offline source audit**, not a runtime-health or hardware-validation report. Only this document is changed. No robot, HTTP service, Docker daemon, broker or external network was contacted; no `.env`, `.local`, token file or private runtime-state contents were read. Paths to private files below are declarations found in source, not inspected files. Concurrent calibration, description and manipulation changes are left intact; citations describe the working-tree source observed during this audit and may shift with that work.

Citations are repository-relative `path:line` or `path:start-end`. An import proves a dependency, not that every export executes. **Production** below means reachable from the normal service/browser/MCP entrypoints by source imports; utilities, tests and research are separated. Type-only references are identified where they could otherwise imply runtime ownership. A missing import in the reviewed source graph is not a license to delete a module or historical script.

**Approved target, not current implementation:** repository name `RRsZ70_ROS2`; root `src/` contains ament packages `z70_driver`, `z70_interfaces`, `z70_description`, `z70_odometry`, `z70_mapping`, `z70_manipulation`, `z70_bringup`; private TypeScript vendor implementation belongs under `adapters/vendor/`, browser code under `apps/web/`, deployment under `deploy/`. ROS owns robot semantics; one vendor driver owns device/vendor transport. rclpy clients remain ament packages. This audit does not move directories, rename packages, implement a driver, introduce launch tooling or change contracts/code.

## 6. Migration constraints exposed by the source audit

1. **Do not move only `ros2/src`.** Root TS entrypoints, Docker COPY/CMD, web build output, deployment fixtures, source-relative MCP children and dynamic imports are coupled to current paths (sections 2–3). Target root `src` would collide with current TS source unless migration is coordinated; no collision is resolved in phase 1.
2. **One driver is a target invariant, not today's global enforcement.** Service, onboarding/camera login and explicit probes can create their own vendor clients (`src/service.ts:189`, `src/onboarding.ts:5-7`, `src/driver-main.ts:15`, `src/room-probe.ts:26`, `src/map-probe.ts:58-68`). ROS executor currently reaches that service by HTTP. Future clients must use ROS driver contracts rather than retain parallel direct vendor ownership.
3. **Research labeling is insufficient.** `MANUAL_JOINT_CONTROLS` is a production runtime dependency; other exports of the same file remain fixtures/types. Conversely `camera-observation.ts` and `telemetry.ts` have production-used utility exports without proving runtime use of their semantic classes/functions. Preserve by export and consumer, not filename.
4. **Source-tree resources remain runtime dependencies.** Perception dynamically loads `calibration/front-camera/floor_geometry.py` and `front_camera.json` (`ros2/src/z70_manipulation/z70_manipulation/perception.py:14-19`). Executor also derives repo via `Path(__file__).resolve().parents[4]` (`ros2/src/z70_manipulation/z70_manipulation/executor.py:226`, `ros2/src/z70_manipulation/z70_manipulation/executor.py:240`). Neither is guaranteed by ament install; later packaging must replace or explicitly resource-install those dependencies, not silently assume symlink-install layouts.
5. **Do not package writable evidence as immutable resources.** Chassis calibration output and pickup logs currently live under repo calibration directories (`ros2/src/z70_odometry/z70_odometry/chassis_calibrator.py:118`, `ros2/src/z70_manipulation/z70_manipulation/executor.py:49-60`). Distinguish installed calibration inputs from runtime-produced data; no existing records are moved or overwritten here.
6. **Keep subprocess packaging explicit.** Depth node resolves sibling `depth_worker.py` and worker imports sibling `depth_geometry` (`ros2/src/z70_mapping/z70_mapping/depth_node.py:37-39`, `ros2/src/z70_mapping/z70_mapping/depth_worker.py:14`). A later repackage must preserve installed module locations or change launch/import strategy together, including offline model-cache and separate-environment assumptions.
7. **Dependency manifests need a separate completeness pass before claiming relocatable installation.** Bridge imports requests, YAML, OpenCV, NumPy and ament package lookup (`ros2/src/z70_bridge/z70_bridge/bridge.py:20-24`, `ros2/src/z70_bridge/z70_bridge/bridge.py:61-63`), while its manifest lists ROS packages but not those Python dependencies (`ros2/src/z70_bridge/package.xml:8-16`). Pixi presently supplies several globally (`ros2/pixi.toml:19-21`). This audit records that mismatch; it does not modify manifests or claim a failed installation test.
